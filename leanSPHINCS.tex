\section{The scheme}
\label{sec:scheme}

Same shape as SLH-DSA-128-24 from NIST's recent SP~800-230~\cite{SP800230} (single XMSS layer), with the differences:
  \begin{itemize}
    \item $h = 26$, instead of $22$ (tree height, i.e. height of the only XMSS layer)
    \item $k = 24$, instead of $6$ (number of trees per FORS)
    \item $a = 10$, instead of $24$ (height of each FORS tree)
    \item WOTS$^+$C~\cite{HK22C}, instead of WOTS$^+$. 64 chains of length $w=4$, with a target sum of 120
  \end{itemize}

Properties:

\begin{itemize}
  \item public key: 32 bytes
  \item secret key: 32 bytes
  \item signature size: 5\,684 bytes
  \item verification: 373 compressions (with BLAKE2s)
  \item security: NIST level 1 \cite{FIPS205} (applies to all the usages below) (127 bits SUF in the ROM, and $\approx 64$ bits in the QROM)
  \item lifetime: up to $2^{30}$ signatures.
\end{itemize}

\paragraph{Hash inputs.} Every hash input is $P \concat \mathit{address} \concat \mathit{data}$: the public
parameter (16 bytes), then a 16-byte address: two fields of 4 and 3 bytes, 1 byte for the type of the call
and the step in a chain, and 8 zero bytes.
\begin{itemize}
  \item the encoding uses $\mathit{data} = m\concat R$ ($R$ is the randomizer): the message ends the first block, so $R$ is the
        second block. A pruned signer tries $R = R_0 + i$ for $i = 0, 1, \dots$, with $R_0$ a hash of the secret key and $m$,
        and keeps the first one that lands in its subtree. The first block is hashed once, so each try costs 1
        compression
  \item a FORS tree has no root hash: the FORS public key hashes the two nodes below the root of every tree, which
        saves one hash per tree
  \item the secrets are derived from the secret key two at a time: one hash gives 32 bytes, i.e.\ two chain starts
        or two FORS secrets
\end{itemize}

\section{Usage}

\subsection{Full \texorpdfstring{$2^{30}$}{2\textasciicircum 30} lifetime}

For powerful devices.

\begin{itemize}
  \item lifetime: $2^{30}$ (at 127 bits of security in the ROM)
  \item keygen: $16 \cdot 10^9$ compressions
  \item signing: $93\cdot10^3$ compressions, with a 16~MiB cache
\end{itemize}

\emph{A modern laptop CPU computes around $2^{30}$ SHA2 or BLAKE2s compressions per second.}


\subsection{Pruned: \texorpdfstring{$2.1\cdot10^5$}{210K} lifetime}

For weaker devices. The trick is to trade smaller lifetime for faster keygen, using hypertree pruning~\cite{conduition}: only build one subtree of height 13, and replace the 13 siblings above it by pseudorandom surrogate nodes.

\begin{itemize}
  \item lifetime: $2.1\cdot10^5$ signatures (at 127 bits of security in the ROM)
  \item keygen: $2.0\cdot10^6$ compressions
  \item signing: $74\cdot10^3$ compressions, with a 16~KiB cache (including $8\cdot10^3$ compressions of grinding)
\end{itemize}

\emph{A Ledger Nano S+ can compute $33$ (resp $25$) thousand BLAKE2s (resp SHA2) per second.}

\subsection{Pruned: \texorpdfstring{$2.2\cdot10^7$}{22M} lifetime}

For laptops, phones and powerful hardware wallets. The same pruning, with a subtree of height 20 (and 6
surrogate siblings).

\begin{itemize}
  \item lifetime: $2.2\cdot10^7$ signatures (at 127 bits of security in the ROM)
  \item keygen: $254\cdot10^6$ compressions
  \item signing: $70\cdot10^3$ compressions, with a 1~MiB cache (including 64 compressions of grinding)
\end{itemize}

\subsection{Threshold signing}
\label{sec:threshold}

\begin{itemize}
  \item $t$-of-$n$
  \item signing: malicious security against $t-1$ operators (with abort); 432 bytes per signer, 3 rounds
  \item keygen: no trusted dealer, a one-time MPC among the $n$ operators, fewer than $n/2$ corrupt
  \item lifetime: $7.5\cdot10^3$, $2.85\cdot10^4$ or $1.08\cdot10^5$ signatures, with a pruned subtree of $2^b$ leaves, $b=8$,
        10 or 12
\end{itemize}

\paragraph{Idea (adapted from PRAWNS~\cite{PRAWNS}).} Each FORS secret is $F(\mathit{addr})$, for a
threshold PRF $F$: $t$ operators evaluate it together, $t-1$ learn nothing (context-aware, see below).
\begin{itemize}
  \item keygen (MPC): computes and publishes all FORS leaves $\hash(F(\mathit{addr}))$, and the signature of
        each FORS root by its WOTS key
  \item signing: the $t$ signers evaluate $F$ at the 24 FORS addresses selected by the message; everything
        else (FORS paths, WOTS signature, authentication path) is read from the public data
\end{itemize}

\paragraph{Choice of $F$.}
\begin{itemize}
  \item hash-based, for small $\binom{n}{t-1}$: replicated seeds~\cite{CDI05}, one seed $k_T$ per set $T$ of $t-1$
        operators, held by the others; $F(x)=\bigoplus_T\hash(k_T,x)$. Hash only
  \item lattice-based, for large $\binom{n}{t-1}$: the threshold PRF of PRAWNS~\cite{PRAWNS},
        $F(x)=\lfloor\langle\hash(x),\mathit{msk}\rangle\rceil_p$, $\mathit{msk}$ Shamir-shared. LWE
\end{itemize}
\paragraph{Context-awareness~\cite{PRAWNS}.} To reveal $F(x)$ when a quorum $J$ signs $m$, each signer
$i\in J$ sends a part, and the parts combine into $F(x)$:
\begin{itemize}
  \item hash-based: each term $\hash(k_T,x)$ is assigned to one signer of $J$ holding $k_T$. Signer $i$ sends
        the XOR of its terms and of $\hash(k_{ij},x,m,J)$ for each co-signer $j$, with $k_{ij}$ a key shared by
        $i$ and $j$: each mask is sent twice and cancels, so the parts XOR to $F(x)$
  \item lattice-based: as in PRAWNS, a rounded share $\lfloor\lambda_i\langle\hash(x),\mathit{sk}_i\rangle\rceil_p$
        plus a rounded share of zero evaluated at $(x,m,J)$; the sum is $F(x)$ up to $\pm t$, and the
        candidates are checked against the public leaf
\end{itemize}
Parts from signings of different $(m,J)$ don't combine, so aborted signings reveal no FORS secret.

\paragraph{Keygen.} Honest-majority MPC, malicious with abort:
\begin{enumerate}
  \item coin tossing: $P$, the kept subtree, its $26-b$ surrogates
  \item the key of $F$ (hash-based: each seed by commit-reveal among its holders; lattice-based: a
        verifiable Shamir sharing of $\mathit{msk}$), and the pairwise keys $k_{ij}$
  \item MPC: $F$ at the $2^b\cdot24\cdot2^{10}$ FORS addresses, hashed into leaves; $F$ at the
        $2^b\cdot64$ WOTS chain starts, hashed 3 times. Open the leaves and chain ends
  \item in the clear: FORS roots, WOTS$^+$C counters; open the WOTS signatures; build the tree
  \item the operators check they all got the same public data (public key, FORS leaves, WOTS signatures;
        1.6~GB for $b=12$) by comparing its hash. Each keeps the public data and its key share of $F$, and
        deletes everything else
\end{enumerate}

\paragraph{Signing (any $t$).}
\begin{enumerate}
  \item agree on $m$
  \item each signer commits to a random $r_i$, then reveals it; $R_0=\hash(r_1,\dots,r_t,m)$, and the signers
        take the first $R=R_0+i$ that lands in the kept subtree.
  \item open $F$ at the 24 FORS addresses; check each against its leaf
  \item output $R$, the 24 secrets and paths, the WOTS signature, the authentication path
\end{enumerate}

\paragraph{Keygen cost (measured, hash-based $F$, $t=(n+1)/2$).} $\approx2.5\cdot10^4\cdot2^b$ MPC hashes (mostly FORS leaves) of
$\approx13.5\cdot10^3$ AND gates. The MPC uses replicated sharing over $\mathrm{GF}(2)$ as
in~\cite{BGIN19}, generalized to $n=2f+1$: each AND gate is computed locally and reshared through one
collector, $(n-1)+f$ bits in total, i.e.\ 1, 1.2 and 1.29 bits per operator for $n=3$, 5, 7, plus a
check~\cite{GS20} of negligible traffic. Traffic per operator:

\begin{center}
\begin{tabular}{lrrr}
  \toprule
  subtree & $2^8$ & $2^{10}$ & $2^{12}$ \\
  lifetime & $7.5\cdot10^3$ & $2.85\cdot10^4$ & $1.08\cdot10^5$ \\
  \midrule
  2-of-3 & 11~GB & 43~GB & 172~GB \\
  3-of-5 & 13~GB & 52~GB & 207~GB \\

\paragraph{Remarks.}
\begin{itemize}
  \item With a trusted dealer instead, keygen needs no MPC: the dealer computes everything in the clear
        ($5\cdot10^8$ to $4\cdot10^9$ compressions for $b=12$, from 2-of-3 to 4-of-7 with the hash-based
        $F$) and gives each operator its key share of $F$.
  \item The key shares can be refreshed, and the committee changed (including $n$ and $t$), with the same
        public key:
  \begin{itemize}
    \item hash-based:
    \begin{enumerate}
      \item the new committee generates fresh seeds for its own $n'$, $t'$ (as at keygen): they define a
            new PRF $F'$
      \item an MPC among $t$ old and the new operators computes, for each FORS address $x$, $F(x)$ (checked
            against its leaf) and $F'(x)$, and opens $c(x)=F(x)\oplus F'(x)$, which is published (it reveals
            nothing: $F'(x)$ masks $F(x)$). About one MPC hash per address, as at keygen
      \item from then on, the secret at $x$ is $F'(x)\oplus c(x)$, which equals $F(x)$: signing uses $F'$
            and the public $c$
      \item new pairwise keys are generated, and the old seeds are deleted
    \end{enumerate}
    \item lattice-based: $t$ old operators reshare $\mathit{msk}$ to the new committee, with threshold $t'$
  \end{itemize}
\end{itemize}

\section{Smaller signatures: a two-level WOTS forest}
\label{sec:twolevel}

FORS can be replaced by a few-time signature (FTS) built from small WOTS keys. Signatures are 25\% smaller
and verification 18\% cheaper, with the same signing cost and longer lifetimes, proved in Lean~\cite{proofs}. The idea is
inspired by Jonas Nick's (Blockstream) sig.golf submission~\cite{siggolf}.

\begin{center}
\begin{tabular}{lrrr}
  \toprule
  FTS & size & verification & FTS signing \\
  \midrule
  FORS, $k=24$, $a=10$ (\cref{sec:scheme}) & 5\,684 bytes & 373 compressions & $61\cdot10^3$ compressions \\
  two-level WOTS forest & 4\,276 bytes & 307 compressions & $61\cdot10^3$ compressions \\
  \bottomrule
\end{tabular}
\end{center}

\paragraph{WOTS keys.} The FTS is built from small WOTS keys: 6 chains of length 5, with leaf
$\hash(\text{6 chain tops})$. A codeword is a vector $d\in\{0,\dots,4\}^6$ with $\sum_i d_i=5$; there are 246 of them.
Signing at $d$ reveals each chain $d_i$ steps below its top. The verifier hashes up to the tops: always 5
steps. The fixed sum acts as the checksum: from one signature, hashing forward cannot reach any other codeword. From
several signatures by the same key, it reaches exactly the codewords below their componentwise max.

\paragraph{Trees.} The FTS has 8 independent trees of height 4, and its public key hashes their 8 roots. Each of
the 16 leaves of a tree is $\hash(R_0,R_1)$, where $R_0$ and $R_1$ are the roots of two subtrees of height 3 over 8
WOTS keys each. In each tree, the message picks a leaf, and in both of its subtrees a WOTS key and a codeword. As for FORS, a tree or a subtree has
no root hash: in $\hash(R_0,R_1)$ and in the public key, $R$ stands for the two nodes just below the root.

\paragraph{Encoding.} Bit fields and one 256-entry table, and every digest is accepted. Each tree takes 26 bits:
4 for the leaf, then, per subtree, 3 for the WOTS key and 8 for a table index. The 16 table indices are the first
16 bytes of the digest; its last 16 bytes, as a little-endian integer, hold the instance index, then the 8 leaves,
then the 16 WOTS keys, so no field lies across two 64-bit words. The table has 256 entries, chosen among
the 246 codewords to maximize the lifetime: spread-out codewords are easier to forge once a key has signed twice, so
the 32 most spread-out ones are left out, and 42 of the most concentrated ones appear twice (all those with digits
4 and 1, and 12 of those with digits 3 and 2). The table is in the Lean model~\cite{proofs}. With the 26 bits of the instance index, the digest is 234 bits,
so it still takes one hash.

\paragraph{Costs.} Per tree:
\begin{itemize}
  \item size: 22 values, i.e.\ 6 chain values and 3 nodes per subtree, plus 4 nodes in the tree
  \item verification: 23 compressions, i.e.\ per subtree 5 chain steps, 2 for the leaf and 2 for the path, then 2 for
        $\hash(R_0,R_1)$ and 3 for the path in the tree
  \item signing: $16\cdot2\cdot8 = 256$ WOTS keys of 29 compressions each
\end{itemize}
Every signature has the same size and verification cost, and keygen is unchanged.

\paragraph{Security.} A forgery at an instance with $r$ prior signatures needs every tree to be covered: in
both subtrees, the target WOTS key must have been opened, and the target codeword must lie below the componentwise
max of those openings. Let $f_t$ be the probability that $t$ random signatures by one WOTS key cover a random codeword
($f_1=0.0052$, $f_2=0.067$, $f_3=0.17$). Then
\[
\mathrm{cover}(r)=\Big(\sum_{u\ge1}\mathrm{Bin}(r,\tfrac1{16})(u)\Big[\sum_{t\ge1}\mathrm{Bin}(u,\tfrac18)(t)\,f_t\Big]^2\Big)^8 .
\]
The lifetime is the largest $N$ with $2^{127}\,2^{b-26}\,\mathbb{E}_{r\sim\mathrm{Poisson}(N/2^b)}[\mathrm{cover}(r)]\le1$.
This is the rule that defines the best known attack on FORS~\cite{proofs}, and the two-level forest is about 20\%
ahead at every subtree height. The last two rows are the lifetimes proved in Lean~\cite{proofs} (rounded down): an adversary
making $q$ hash queries forges with probability at most $q\cdot2^{-127}$.

\paragraph{Threshold signing.} In \cref{sec:threshold}, a signature reveals FORS secrets, which are outputs $F(\mathit{addr})$
of the threshold PRF, so signing needs no MPC. Here a signature reveals $x_{i,4-d_i}$, i.e.\ the secret hashed
$4-d_i$ times, which no threshold PRF outputs. As for the key refresh, the keygen publishes these values encrypted
under $F$:
\begin{itemize}
  \item position 0, the secret: $F(\mathit{addr})$, as before
  \item positions $j = 1$ to 3: computed by the keygen MPC, and published as $x_{i,j} \oplus F(\mathit{addr}_{i,j})$, for a
        fresh address $\mathit{addr}_{i,j}$
  \item position 4, the top: published
\end{itemize}
Revealing $x_{i,j}$ is then one context-aware evaluation of $F$, as for a FORS secret, so signing still needs no MPC.
Each signer sends a part for every revealed value below the top: 48 on average and at most 80, instead of 24. Per
instance of the kept subtree:
\begin{itemize}
  \item keygen MPC: 4 hashes per chain, $2048\cdot6\cdot4 = 49\,152$, instead of $24\cdot2^{10} = 24\,576$ FORS leaves:
        about twice the traffic
  \item public data: 4 values per chain (the top and 3 encrypted values), $2048\cdot6\cdot4\cdot16$~B $= 768$~KiB instead
        of 384~KiB of FORS leaves, e.g.\ 3.2~GB instead of 1.6~GB for $b=12$
\end{itemize}
