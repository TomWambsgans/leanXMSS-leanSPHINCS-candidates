\section{The scheme}

Same shape as SLH-DSA-128-24 from NIST's recent SP~800-230~\cite{SP800230} (single XMSS layer), with the differences:
  \begin{itemize}
    \item $h = 26$, instead of $22$ (tree height, i.e. height of the only XMSS layer)
    \item $k = 24$, instead of $6$ (number of FORS trees)
    \item $a = 10$, instead of $24$ (height of each FORS tree)
    \item WOTS$^+$C~\cite{HK22C}, instead of WOTS, with a target sum of 120
  \end{itemize}

Properties:

\begin{itemize}
  \item public key: 32 bytes
  \item secret key: 32 bytes
  \item signature size: 5\,684 bytes
  \item verification: 391 compressions (with BLAKE2s)
  \item security: NIST level 1 \cite{FIPS205} (applies to both usage cited bellow) (127 bits SUF in the ROM, and $\approx 64$ bits in the QROM)
  \item lifetime: up to $2^{30}$ signatures.
\end{itemize}

\section{Usage}

\subsection{Full \texorpdfstring{$2^{30}$}{2\textasciicircum 30} lifetime}

For powerfull devices.

\begin{itemize}
  \item lifetime: $2^{30}$
  \item keygen: $19 \cdot 10^9$ compressions
  \item signing 
    \begin{itemize}
    \item with a 1~MiB cache: $421\cdot10^3$ compressions
    \item with a 1~GiB cache: $75\cdot10^3$ compressions
  \end{itemize}
\end{itemize}

\emph{Modern laptop CPUs can compute on the order of a $10^9$ SHA2 or BLAKE2s compressions per second.}


\subsection{Pruned: \texorpdfstring{$2^{16}$}{2\textasciicircum 16} lifetime}\label{sec:pruned}

For weaker devices. The trick is to trade smaller lifetime for faster keygen, using hypertree pruning~\cite{conduition}: only build one subtree of height 12, and replace the 14 siblings above it by pseudorandom surrogate nodes.

\begin{itemize}
  \item lifetime: $2^{16}$
  \item keygen: $1.1\cdot10^6$ compressions
  \item signing: $142\cdot10^3$ compressions, with a 16~KiB cache (including $66\cdot10^3$ compressions of grinding)
\end{itemize}

\emph{A Ledger Nano S+ can compute $33$ (resp $25$) thousand BLAKE2s (resp SHA2) per second.}

\subsection{Threshold signing (MPC)}

A concrete example of what's possible:
\begin{itemize}
  \item 3-of-4: any 3 operators can sign, and the verifier doesn't change
  \item lifetime: $2^{16}$ signatures, using the same hypertree pruning as in \cref{sec:pruned}
  \item malicious security against 1 corrupt operator: alone it can neither sign nor learn anything about
        the key, and if it deviates it is identified and the others sign without it (but 2 colluders can
        rebuild the key, unlike 3-of-4 BLS)
  \item DKG: no trusted dealer
  \item share refresh: the shares can be refreshed, and an operator replaced, with the same public key
  \item keygen: $786\cdot10^3$ MPC hashes, about 2.2~GB of traffic per operator and 2\,500 rounds (assuming
        BLAKE2s)
  \item signing: at most one new FORS instance to compute in MPC, $24\,696$ MPC hashes, about 68~MB of
        traffic per operator and 2\,600 rounds. Either:
    \begin{itemize}
    \item trivially, once the message is known: grind as in a plain pruned key ($66\cdot10^3$
          compressions), then compute the instance the message selects, if it is new
    \item or with preprocessing: compute the instance before the message is known. Online, no MPC: only
          $2.7\cdot10^8$ compressions of grinding in the clear (about 0.3~s) and 2 rounds of about 1~KB
          per operator
    \end{itemize}
\end{itemize}

\paragraph{Where the secrets are used.} A signer only uses its secrets in three places:
\begin{itemize}
  \item WOTS: each chain starts at a secret and is hashed forward, to its end at keygen (the ends make the
        leaf) and to the signed position at signing
  \item FORS: each leaf is the hash of a secret
  \item the randomizer: a hash of a secret and the message
\end{itemize}
Everything else (the XMSS tree, the FORS trees above the leaves, the WOTS$^+$C counter search) only hashes
public values. So the operators keep the secrets shared, compute only these hashes jointly, and open only
what the signature reveals. Moreover, the WOTS and FORS hashes don't depend on the message, which only
selects the FORS instance and the 24 secrets to open. So they can be computed before the message is
known, if we fix the instance in advance and grind the randomizer until the message selects it.

\paragraph{Sharing the secrets.} Usually each secret is a hash of the secret key and its address, which
would already need MPC. Instead there are 4 seeds: $k_i$ is known to every operator except $i$, and each
secret is $\bigoplus_i\hash(k_i,\mathit{addr})$~\cite{CDI05}. By hashing its 3 seeds, each operator gets a
share of every secret, without any interaction. One operator misses its own seed, so it learns nothing;
any 2 hold all seeds.

\paragraph{Keygen (DKG).}
\begin{enumerate}
  \item each $k_i$ is sampled by an operator other than $i$ and sent to the two others, who compare its
        hash. So the seed a corrupt operator misses comes from an honest one.
  \item the public parameter and the 14 surrogate nodes come from commit-reveal coin tossing, so that no
        operator can pick a surrogate with a subtree it knows below.
  \item MPC hashes the 64 chains of each of the $2^{12}$ kept leaves to their ends ($786\cdot10^3$ hashes)
        and opens the ends. The tree is built in the clear, and its root is the public key.
\end{enumerate}

\paragraph{Signing.} The $j$-th signature uses the FORS instance given by a hash of the public parameter
and $j$: random as in a plain pruned key (so the security is the same), but known in advance.
\begin{itemize}
  \item preprocessing, if the instance is new: MPC hashes its $24\,576$ secrets into leaves and opens
        them. The FORS trees and the WOTS$^+$C counter search run in the clear, then MPC walks the WOTS
        chains to the signed positions (120 hashes) and opens them. All of it is cached for later uses
        of the instance.
  \item online, for a message $m$: open $R_0=\bigoplus_i\hash(k_i,m)$ (local hashes, no MPC). Every
        operator grinds $R=\hash(R_0,\mathit{ctr})$ until $m$ selects the instance ($2^{26}$ tries),
        keeping the first counter that works. Then open the 24 selected FORS secrets.
\end{itemize}

\paragraph{Cheaters.} The MPC protocol is maliciously secure, and every opened value is checked: against
public data (a FORS leaf, a chain end) or by majority (each term of $R_0$ is sent by 3 operators). So a
cheater is caught and identified, and the others retry without it, with the same $R$.

\paragraph{Share refresh.} The public key only fixes the WOTS chain starts, and a FORS instance is only
fixed once its WOTS key signs it. So the shares can be refreshed with the same public key:
\begin{enumerate}
  \item each operator turns its seeds into explicit shares of what is fixed and still needed: the chain
        starts of the unused leaves (at most $2^{18}$) and the FORS secrets of the used instances
        ($24\,576$ each).
  \item each operator deals a random sharing of zero, which is added to these shares: same values, fresh
        shares. Holders compare hashes of what they receive, and a masked random linear combination is
        opened to check that each dealt sharing is really zero (otherwise a cheater could shift the
        secrets and break the key).
  \item new seeds are sampled as in keygen, for the new instances and randomizers, and the old seeds and
        shares are deleted.
\end{enumerate}
To replace an operator, the newcomer first gets the terms it takes over from their other holders. This
costs no MPC hash, a few rounds, and from 13~MB per operator for a fresh key to 5~GB once all instances
are used. It
protects against an attacker who corrupts one operator per period, as long as old shares are really
deleted.

\paragraph{MPC cost.} An MPC hash is a BLAKE2s compression on a secret input, about $14.7\cdot10^3$ AND
gates (XOR is free). What matters is the traffic per AND gate per operator, with malicious security:
\begin{itemize}
  \item about 1 bit: 3 operators, $f=1$~\cite{BGIN19} (more CPU), e.g.\ when only 3 are online
  \item about 1.5 bits: 4 operators, $f=1$~\cite{FF21} (caveat~\cite{BS26}), the numbers above
  \item about 10 bits: 3 operators with simpler cut-and-choose~\cite{FLNW17}, or bigger clusters (e.g.\
        10-of-15) with packed Shamir sharing
  \item tens of bits: bigger clusters with plain Shamir sharing~\cite{ATLAS21}
\end{itemize}
Rounds: each layer of AND gates costs one round, and all the hashes of a layer run together. A BLAKE2s
compression has AND-depth 884 (with ripple-carry adders, as in the AND count above), so a WOTS chain of 3
hashes takes 2\,500 rounds: about 2 minutes at 50~ms per round, 2.5~s at 1~ms. Parallel-prefix adders
would halve the depth, for 4 times the AND gates. The malicious-security checks add a few rounds, and
preprocessing can run several instances at once, since they are known in advance.

Everything works for $n$ operators with $f<n/2$ corrupt, with one seed per set of $f$ operators, known to
the others. Without an honest majority, MPC costs orders of magnitude more.
