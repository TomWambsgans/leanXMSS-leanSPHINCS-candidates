\section{The scheme}

Same shape as SLH-DSA-128-24 from NIST's recent SP~800-230~\cite{SP800230} (single XMSS layer), with the differences:
  \begin{itemize}
    \item $h = 26$, instead of $22$ (tree height, i.e. height of the only XMSS layer)
    \item $k = 24$, instead of $6$ (number of FORS trees)
    \item $a = 10$, instead of $24$ (height of each FORS tree)
    \item WOTS$^+$C~\cite{HK22C}, instead of WOTS, with a target sum of 120
  \end{itemize}

Properties:

\begin{itemize}
  \item public key: 32 bytes
  \item secret key: 32 bytes
  \item signature size: 5\,684 bytes
  \item verification: 391 compressions (with BLAKE2s)
  \item security: NIST level 1 \cite{FIPS205} (applies to both usage cited bellow) (127 bits SUF in the ROM, and $\approx 64$ bits in the QROM)
  \item lifetime: up to $2^{30}$ signatures.
\end{itemize}

\section{Usage}

\subsection{Full \texorpdfstring{$2^{30}$}{2\textasciicircum 30} lifetime}

For powerfull devices.

\begin{itemize}
  \item lifetime: $2^{30}$
  \item keygen: $19 \cdot 10^9$ compressions
  \item signing 
    \begin{itemize}
    \item with a 1~MiB cache: $421\cdot10^3$ compressions
    \item with a 1~GiB cache: $75\cdot10^3$ compressions
  \end{itemize}
\end{itemize}

\emph{Modern laptop CPUs can compute on the order of a $10^9$ SHA2 or BLAKE2s compressions per second.}


\subsection{Pruned: \texorpdfstring{$2^{16}$}{2\textasciicircum 16} lifetime}

For weaker devices. The trick is to trade smaller lifetime for faster keygen, using hypertree pruning~\cite{conduition}: only build one subtree of height 12, and replace the 14 siblings above it by pseudorandom surrogate nodes.

\begin{itemize}
  \item lifetime: $2^{16}$
  \item keygen: $1.1\cdot10^6$ compressions
  \item signing: $142\cdot10^3$ compressions, with a 16~KiB cache (including $66\cdot10^3$ compressions of grinding)
\end{itemize}

\emph{A Ledger Nano S+ can compute $33$ (resp $25$) thousand BLAKE2s (resp SHA2) per second.}

\subsection{Threshold signing (MPC)}

What we get, with a pruned key ($2^{16}$ signatures):
\begin{itemize}
  \item 3-of-4: 4 operators, any 3 can sign, and the verifier doesn't change
  \item malicious security against 1 corrupt operator: alone it can neither sign nor learn anything about
        the key, and if it deviates it is identified and the others sign without it (but 2 colluders can
        rebuild the key, unlike 3-of-4 BLS)
  \item DKG: no trusted dealer, nobody ever sees the key
  \item keygen: $786\cdot10^3$ MPC hashes, about 2.2~GB of traffic per operator
  \item signing, preprocessing (before the messages are known): $24\,576$ MPC hashes, about 68~MB per
        operator, once every 16 signatures
  \item signing, online: no MPC, $2.7\cdot10^8$ compressions of grinding in the clear (about 0.3~s) and
        2 rounds of about 1~KB per operator
\end{itemize}

\paragraph{Idea.} Only hashes with a secret input need MPC: the WOTS chain steps and the FORS leaf hashes.
Everything else runs in the clear: the XMSS tree, the FORS trees above the leaves, the grinding, the
WOTS$^+$C counter search. A FORS instance depends only on its leaf, not on the message, so it can be
computed in MPC in advance; at signing time we grind the randomizer until the message lands on it.

\paragraph{Secrets.} Usually each secret is a hash of the secret key and the secret's address, which would
need MPC on a shared secret key. Instead there is no secret key but 4 seeds: $k_i$ is known to every
operator except $i$, and each secret is $\bigoplus_i\hash(k_i,\mathit{addr})$~\cite{CDI05}. Each operator
hashes its 3 seeds, which gives it a share of every secret without any interaction. One operator misses
its own seed, so it learns nothing; two hold all seeds.

\paragraph{Keygen (DKG).}
\begin{enumerate}
  \item each $k_i$ is sampled by an operator other than $i$ and sent to the two others, who compare its
        hash. So the seed a corrupt operator misses comes from an honest one.
  \item the public parameter and the 14 surrogate nodes come from commit-reveal coin tossing, so that no
        operator can pick a surrogate with a subtree it knows below.
  \item MPC runs the 3 steps of the 64 chains of each of the $2^{12}$ kept leaves ($786\cdot10^3$ hashes),
        opens the endpoints and keeps shares of the intermediate positions. The rest of the tree is
        built in the clear, and its root is the public key.
\end{enumerate}

\paragraph{Signing.} The $2^{12}$ FORS instances are used in a fixed order, each for exactly 16 signatures.
\begin{itemize}
  \item preprocessing, for the next instance: MPC hashes its $24\,576$ secrets into leaves, which are
        opened. The FORS trees and the WOTS$^+$C counter search run in the clear, then the WOTS chain
        values are opened (the WOTS signature is the same for the 16 signatures of the instance).
  \item online, for a message $m$: open $R_0=\bigoplus_i\hash(k_i,m)$ (local hashes, no MPC), which nobody
        can predict. Every operator grinds $R=\hash(R_0,\mathit{ctr})$ until the digest's leaf index is
        the current instance ($2^{26}$ tries), keeping the first counter that works. Then open the 24
        FORS secrets selected by the digest.
\end{itemize}
Each opened value is checked, against public data (a FORS leaf, a chain endpoint) or by majority (each
term of $R_0$ is sent by 3 operators), so a bad share is caught and its sender identified. The others
retry without it, with the same $R$. Using each instance exactly 16 times is safer than the random use of
a plain pruned key: the FORS reuse term is $2^{-144}$ instead of $2^{-130}$.

\paragraph{Cost.} An MPC hash is a BLAKE2s compression on a secret input, about $14.7\cdot10^3$ AND gates
(XOR is free). What matters is the traffic per AND gate per operator, with malicious security (corrupt
operators may deviate arbitrarily):
\begin{itemize}
  \item about 1 bit: 3 operators, $f=1$~\cite{BGIN19} (more CPU), e.g.\ when only 3 are online
  \item about 1.5 bits: 4 operators, $f=1$~\cite{FF21} (caveat~\cite{BS26}), the numbers above
  \item about 10 bits: 3 operators with simpler cut-and-choose~\cite{FLNW17}, or bigger clusters (e.g.\
        10-of-15) with packed Shamir sharing
  \item tens of bits: bigger clusters with plain Shamir sharing~\cite{ATLAS21}
\end{itemize}
Everything works for $n$ operators with $f<n/2$ corrupt, with one seed per set of $f$ operators, known to
the others. Without an honest majority, MPC costs orders of magnitude more.
